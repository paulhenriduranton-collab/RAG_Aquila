Principe clé : séparer exécution et scoring

  • run_agentic_all.py fait tourner le vrai graph agentique une seule fois — coûteux en appels LLM
  • evaluate_components.py lit les résultats déjà capturés et ne fait que du scoring — rejouable à volonté
  • On peut ajuster une métrique ou un prompt de juge sans refaire tourner le pipeline
  • Seul cas de ré-exécution : si on modifie agent.py/ask.py eux-mêmes

Pourquoi instrumenter agent.py plutôt que dupliquer ?

  • Une version antérieure rejouait la logique dans un script séparé — risque de divergence
  • agent.py a 8 champs debug dans AgentState : pre_rerank_docs, docs_before_rewrite, pre_dedup_docs, semantic_docs, bm25_docs, dedup_removed_docs, dedup_kept_docs, grading_before_rewrite
  • Garantit que les données d'évaluation reflètent exactement le comportement réel
  • run_agent() retourne l'état final complet (tous les champs, y compris debug)

Structure JSON d'un résultat debug

  • id : identifiant structuré (ex: L1_ENS_001)
  • question + reponse_attendue : depuis questions.json
  • reponse_llm : réponse réellement générée
  • router : {sources, difficulty} — prédictions du LLM
  • pre_rerank_docs : chunks avant le cross-encoder
  • post_rerank_docs : chunks après re-ranking, avant rewrite
  • grading : {performed, sufficient, verdict} — si rewrite déclenché, c'est le snapshot du grading qui l'a causé (grading_before_rewrite), pas le grading final
  • rewrite : {triggered, new_query, chunks_loop_1/2, grading_after} — grading_after = verdict du grading final sur le pool post-rewrite
  • chunks : pool final (ce que generate_node a réellement reçu)
  • pre_dedup_docs / semantic_docs / bm25_docs : intermédiaires pour l'éval ⑧ (déjà disponibles)
  • dedup_removed_docs / dedup_kept_docs : paires (écarté, conservé) pour l'éval ⑦ (nécessite un re-run)

Déduction sans champ supplémentaire

  • Rewrite déclenché ? → attempts ≥ 2 (2ème retrieval = reformulation)
  • Grading a eu lieu ? → initial_difficulty > 1 (diff 1 = pas de grading)
  • Grading après rewrite ? → jamais (MAX_ATTEMPTS=1 → generate direct)
  • post_rerank_docs = docs_before_rewrite si rewrite, sinon = chunks finaux

Comment RAGAS juge (gemma2:2b)

  • ContextPrecision : pour chaque chunk, le LLM juge s'il est pertinent vis-à-vis de la reference → proportion pondérée par rang
  • ContextRecall : le LLM découpe la reference en affirmations atomiques → vérifie si chacune est attribuable à au moins un chunk
  • Les 4 appels RAGAS (precision/recall × pre/post) sont lancés en parallèle via asyncio.gather
  • MRR (③bis) : un LLM-juge labellise chaque chunk pertinent/non pertinent ; mesure la position du premier chunk pertinent, avant et après re-ranking

Optimisation

  • Si pre == post (pool ≤ K_FINAL), _rerank() n'a jamais été invoqué dans agent.py
  • Un seul scoring suffit — le delta serait de toute façon nul
  • Économise 2 appels LLM par question dans ce cas

Pourquoi le même modèle comme juge ?

  • Le juge externe est le même gemma4:12b que le grader évalué
  • Seule différence : le prompt du juge inclut la réponse attendue
  • Avantage : pas de modèle supplémentaire à télécharger/configurer
  • Limite : biais de cohérence possible (un modèle qui se juge lui-même)
  • Alternative plus rigoureuse : utiliser gemma2:2b ou un tiers modèle comme juge

Interprétation de la matrice

  • Faux Négatifs (FN) fréquents → le grader est trop sévère, déclenche des rewrites inutiles
  • Faux Positifs (FP) fréquents → le grader est trop laxiste, rate des informations manquantes
  • Un bon grader maximise TP + TN (accuracy élevée)
  • Precision élevée → quand il dit OUI, on peut lui faire confiance
  • Recall élevé → il détecte bien tous les cas réellement suffisants

Ce que cette brique mesure vraiment

  • Pas juste "est-ce que la reformulation sonne mieux" — mais est-ce que le retrieval a concrètement rapporté plus d'info pertinente
  • La baseline n'est pas recalculée (0 appel LLM supplémentaire) — elle vient directement de la brique ②
  • Le pool "après" est exactement celui produit par le vrai pipeline (3 anciens + 2 nouveaux), pas un pool reconstruit artificiellement
  • Taux de réussite (rewrite_success) : le grading final (sur le pool post-rewrite) dit-il OUI ?
  • Ciblage (rewrite_targeted) : un LLM-juge vérifie si la nouvelle requête vise bien le manque identifié par le grading qui a déclenché la reformulation

Pourquoi Faithfulness et pas AnswerCorrectness ?

  • Faithfulness mesure si le LLM reste fidèle aux chunks — pas s'il a raison ou tort par rapport à la ground truth
  • C'est une mesure d'hallucination pure : "le LLM invente-t-il des choses ?"
  • Si les chunks sont bons mais la réponse invente → problème de génération (cette brique le détecte)
  • Si les chunks sont mauvais mais la réponse les suit fidèlement → problème de retrieval (briques ②③ le détectent)
  • AnswerCorrectness mélange les deux responsabilités — ici on les isole

Chunks utilisés = les vrais

  • On utilise toujours entry['chunks'] — le pool réellement fourni à generate_node
  • Si un rewrite a eu lieu, c'est le pool post-rewrite (3+2 fusionnés)
  • Sinon, c'est le pool direct du 1er retrieval
  • La fidélité est mesurée par rapport à ce qui a vraiment servi, pas un pool reconstruit

Limites Connues
Biais et compromis de cette approche d'évaluation

④ Grading — Biais de cohérence

  • Le juge externe utilise le même modèle (gemma4:12b) que le grader évalué
  • Seul le prompt diffère (le juge voit la ground truth)
  • Un modèle indépendant (gemma2:2b ou un tiers) serait un juge plus rigoureux
  • Compromis : coût d'un appel LLM supplémentaire vers un modèle différent

③ Re-ranking — Granularité limitée

  • pre_rerank_docs capture le pool fusionné du 1er retrieval uniquement
  • Pour difficulté 3 (sous-requêtes), c'est le pool fusionné de toutes les sous-requêtes avant re-rank global
  • Pas d'état intermédiaire par sous-requête individuelle

Coût en appels LLM par question

  • run_agentic_all.py (exécution, une fois) : le plus coûteux (pipeline complet)
  • evaluate_components.py : 15 à 40 appels gemma2:2b (RAGAS + LLM-juge MRR/dédup/RRF/ciblage rewrite) par question
  • + 1 appel gemma4:12b pour le juge de grading (si difficulté > 1)
  • Total scoring : ~900 appels LLM pour 50 questions

⑦⑧ Données intermédiaires requises

  • ⑧ Fusion RRF : semantic_docs, bm25_docs, pre_dedup_docs — déjà capturés sur le dataset actuel, prêt à scorer
  • ⑦ Déduplication : dedup_removed_docs, dedup_kept_docs — champs plus récents, pas encore présents dans agentic_results_debug.json
  • Sans ces champs, les briques affichent « données non disponibles » sans bloquer les autres
  • Solution pour ⑦ : relancer run_agentic_all.py pour regénérer agentic_results_debug.json
