Principe clé : séparer exécution et scoring

  • run_agentic_all.py fait tourner le vrai graph agentique une seule fois — coûteux en appels LLM
  • evaluate_components.py lit les résultats déjà capturés et ne fait que du scoring — rejouable à volonté
  • On peut ajuster une métrique ou un prompt de juge sans refaire tourner le pipeline
  • Seul cas de ré-exécution : si on modifie agent.py/ask.py eux-mêmes

Pourquoi instrumenter agent.py plutôt que dupliquer ?

  • Une version antérieure rejouait la logique dans un script séparé — risque de divergence
  • agent.py a 2 champs debug dans AgentState : pre_rerank_docs et docs_before_rewrite
  • Garantit que les données d'évaluation reflètent exactement le comportement réel
  • run_agent() retourne l'état final complet (tous les champs, y compris debug)

Structure JSON d'un résultat debug

  • id : identifiant structuré (ex: L1_ENS_001)
  • question + reponse_attendue : depuis questions.json
  • reponse_llm : réponse réellement générée
  • router : {sources, difficulty} — prédictions du LLM
  • pre_rerank_docs : chunks avant le cross-encoder
  • post_rerank_docs : chunks après re-ranking, avant rewrite
  • grading : {performed, sufficient, verdict}
  • rewrite : {triggered, new_query, retrieved_docs, chunks_loop_1/2}
  • chunks : pool final (ce que generate_node a réellement reçu)

Déduction sans champ supplémentaire

  • Rewrite déclenché ? → attempts ≥ 2 (2ème retrieval = reformulation)
  • Grading a eu lieu ? → initial_difficulty > 1 (diff 1 = pas de grading)
  • Grading après rewrite ? → jamais (MAX_ATTEMPTS=1 → generate direct)
  • post_rerank_docs = docs_before_rewrite si rewrite, sinon = chunks finaux

① Router — Comparaison pure

  • Aucun appel LLM — comparaison d'ensembles
  • Source correcte : set(pred) == set(expected)
  • Difficulté correcte : pred == meta["niveau"]
  • Ground truth des sources via eval_common.SOURCE_MAP (scan de documents/)
  • Appliqué sur les 50 questions sans exception

②③ Retrieval + Re-ranking — RAGAS

  • gemma2:2b juge chaque chunk (pertinent ou non vis-à-vis de la reference)
  • ContextPrecision : proportion de chunks pertinents, pondérée par rang
  • ContextRecall : proportion d'affirmations de la reference couvertes par les chunks
  • Optimisation : si pre == post (pool ≤ K_FINAL), un seul scoring (delta = 0)
  • Scoring parallèle via asyncio.gather (même nombre d'appels, temps réduit)

④ Grading — Juge externe custom

  • Le grader réel voit les chunks, PAS la ground truth
  • Le juge externe voit les chunks ET la réponse attendue
  • Même modèle (gemma4:12b) — seul le prompt diffère
  • Matrice de confusion : TP/TN/FP/FN + Precision/Recall/F1
  • Non applicable pour les questions de difficulté 1 (jamais gradées)

⑤⑥ Rewriting + Generation

  • ⑤ Rewriting : mesure le gain concret (pas juste si la reformulation "sonne mieux")
  • Baseline = scores ② réutilisés (pas de 2ème calcul)
  • Pool après rewrite = entry["chunks"], produit par le vrai mécanisme de fusion (3+2)
  • ⑥ Generation : Faithfulness = décompose la réponse en affirmations → chacune vérifiable dans les chunks ?
  • Mesure d'hallucination pure, sans comparer à la reference

Le prompt du juge externe

  • Question + extraits de documents + réponse attendue (ground truth)
  • Demande : "les extraits contiennent-ils suffisamment d'info pour produire la réponse attendue ?"
  • Réponse : OUI / NON — [explication]
  • Utilise _invoke_with_retry() d'ask.py (même gemma4:12b)

Métriques dérivées

  • Accuracy : (TP + TN) / total — accord global
  • Precision (classe OUI) : TP / (TP + FP) — quand le grader dit OUI, a-t-il raison ?
  • Recall (classe OUI) : TP / (TP + FN) — le grader détecte-t-il tous les cas suffisants ?
  • F1 : moyenne harmonique Precision × Recall
  • Limite : même modèle → biais de cohérence possible

Sous-ensembles pertinents

  • ①②③⑥ : calculés sur les 50 questions
  • ④ Grading : seulement sur les questions de difficulté > 1 (grading_performed=1)
  • ⑤ Rewriting : seulement sur les questions où le rewrite a été déclenché (rewrite_triggered=1)
  • Les moyennes sont calculées sur le sous-ensemble pertinent, pas sur les 50

Ventilation par niveau

  • Niveau 1 (11 qs) : factuel — retrieval direct, pas de grading/rewrite
  • Niveau 2 (19 qs) : synthèse — grading activé, rewrite possible
  • Niveau 3 (20 qs) : comparaison — sous-requêtes + reformulation possible
  • Permet de localiser les faiblesses par type de question

⚠
Limites Connues
Biais et compromis de cette approche d'évaluation

④ Grading — Biais de cohérence

  • Le juge externe utilise le même modèle (gemma4:12b) que le grader évalué
  • Seul le prompt diffère (le juge voit la ground truth)
  • Un modèle indépendant (gemma2:2b ou un tiers) serait un juge plus rigoureux
  • Compromis : coût d'un appel LLM supplémentaire vers un modèle différent

③ Re-ranking — Granularité limitée

  • pre_rerank_docs capture le pool fusionné du 1er retrieval uniquement
  • Pour difficulté 3 (sous-requêtes), c'est le pool fusionné de toutes les sous-requêtes avant re-rank global
  • Pas d'état intermédiaire par sous-requête individuelle

Coût en appels LLM par question

  • run_agentic_all.py (exécution, une fois) : le plus coûteux (pipeline complet)
  • evaluate_components.py : 2 à 8 appels gemma2:2b (RAGAS) par question
  • + 1 appel gemma4:12b pour le juge de grading (si difficulté > 1)
  • Total scoring : ~200 à 400 appels LLM pour 50 questions
