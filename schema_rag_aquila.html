Stack Technique

  • LLM : gemma4:12b via Ollama (100% local)
  • Embeddings : bge-m3 (multilingue, 8192 tokens)
  • Re-ranker : BAAI/bge-reranker-v2-m3 (CrossEncoder)
  • Vector Store : ChromaDB (SQLite persistant)
  • Agent : LangGraph (state machine)
  • API : FastAPI (compatible OpenAI)
  • UI : Open WebUI

Points Forts

  • Aucune dépendance cloud — fonctionne hors-ligne
  • Retrieval hybride (sémantique + lexical)
  • Boucle agentique auto-corrective
  • Re-ranking neural pour précision maximale
  • Évaluation RAGAS complète (5 métriques)
  • Découpage intelligent par LLM

Pourquoi un split en 3 étapes ?

  • Pré-split titres : les sections d'un PDF couvrent plusieurs pages — on regroupe par thème d'abord
  • Split LLM : un LLM comprend la sémantique et coupe entre sous-sections logiques, pas au milieu d'un tableau
  • Fallback récursif : filet de sécurité si le LLM produit un chunk trop long (>1500 car.)

Pourquoi un préfixe contextuel ?

  • L'embedding voit la structure du document (source, page, section)
  • Améliore la recherche sémantique sans hallucination du LLM
  • Mots-clés extraits par fréquence (déterministe, pas de LLM)
  • Le re-ranker et le LLM de génération voient aussi cette info

Pourquoi HyDE ?

  • Une question et sa réponse n'ont pas le même vocabulaire
  • HyDE génère une réponse fictive dont l'embedding sera plus proche des vrais passages
  • Activé uniquement pour difficulté > 1 (synthèse/comparaison)
  • Les questions factuelles cherchent des termes exacts → pas besoin

Pourquoi recherche hybride ?

  • Sémantique seule : manque les correspondances exactes (noms propres, acronymes)
  • BM25 seul : ne comprend pas les synonymes ni la sémantique
  • RRF : fusionne par rang (pas par score), robuste quelle que soit la distribution
  • MMR assure la diversité dans les résultats sémantiques

Pourquoi un CrossEncoder pour le re-ranking ?

  • Un bi-encoder (embedding) encode question et document séparément
  • Un cross-encoder encode (question, document) ensemble → bien plus précis
  • Trop lent pour 200+ chunks, mais parfait pour 15 candidats pré-filtrés
  • Seuil à 0.5 : élimine les chunks hors-sujet (score < 0.5)

    direction LR

    [*] --> IdentifySources

    state "🧠 identify_sources()" as IdentifySources {
        direction LR
        note right of IdentifySources
            LLM analyse la question :
            ─ Sources : ENS / Sorbonne / les deux
            ─ Difficulté : 1 (factuel), 2 (synthèse), 3 (comparaison)
            ─ Sous-questions (si difficulté = 3)
        end note
    }

    state "🔍 retrieve_node()" as Retrieve {
        direction LR
        note right of Retrieve
            Tentative 0 :
            ─ Diff. 3 → 1 retrieve/sous-question + fusion
            ─ Diff. 1-2 → 1 retrieve (HyDE si diff > 1)

            Tentative 1 :
            ─ Query reformulée + merge ancien top-3
        end note
    }

    state "📊 grade_documents()" as Grade {
        direction LR
        note right of Grade
            LLM évalue si les chunks suffisent :
            ─ Entités correctes ? (pas de confusion)
            ─ Détails non mélangés ?
            ─ Verdict : OUI ou NON + info manquante
        end note
    }

    state "⬆️ upgrade_difficulty()" as Upgrade {
        direction LR
        note right of Upgrade
            Passe la difficulté à 3
            pour accéder à la reformulation
        end note
    }

    state "🔄 rewrite_query()" as Rewrite {
        direction LR
        note right of Rewrite
            Utilise le verdict du grader
            pour reformuler la requête :
            ─ Cible ce qui manque
            ─ Propose synonymes/mots-clés
        end note
    }

    state "💬 generate_node()" as Generate {
        direction LR
        note right of Generate
            gemma4:12b + prompt contraint
            ─ Uniquement depuis le contexte
            ─ Citation des sources obligatoire
            ─ Calculs si nécessaire
        end note
    }

    state route_after_retrieve <>
    state route_after_grade <>

    IdentifySources --> Retrieve

    Retrieve --> route_after_retrieve

    route_after_retrieve --> Generate : difficulté == 1\n(factuel, pas de grading)
    route_after_retrieve --> Generate : tentatives > MAX (1)
    route_after_retrieve --> Grade : difficulté ≥ 2\net tentatives ≤ MAX

    Grade --> route_after_grade

    Rewrite --> Retrieve : 2e tentative\n(query reformulée)

État de l'Agent (AgentState)

  • question : question originale (immuable)
  • current_query : requête de recherche (peut être reformulée)
  • sources : documents ciblés (None = tous)
  • difficulty : 1=factuel, 2=synthèse, 3=comparaison
  • sub_queries : sous-questions décomposées (si diff=3)
  • docs : pool cumulatif de tous les chunks récupérés
  • sufficient : verdict du grader (OUI/NON)
  • attempts : nombre de retrievals (max 2 : initial + 1 reformulation)
  • answer : réponse finale générée

Les 3 niveaux de difficulté

  • Niveau 1 — Factuel : valeur unique, réponse explicite → retrieve direct, pas de grading
  • Niveau 2 — Synthèse : explication + plusieurs faits d'un même doc → grading activé
  • Niveau 3 — Comparaison : multi-documents ou raisonnement complexe → sous-questions + reformulation possible

Scénarios de parcours

  • Chemin court (factuel) : identify → retrieve → generate (1 appel LLM retrieval)
  • Chemin moyen (synthèse OK) : identify → retrieve → grade=OUI → generate
  • Chemin long (reformulation) : identify → retrieve → grade=NON → upgrade → rewrite → retrieve → generate
  • Chemin comparaison : identify → retrieve (N sous-questions) → grade → [rewrite?] → generate

Métriques RAGAS (score 0→1)

  • Faithfulness : chaque affirmation de la réponse est-elle vérifiable dans le contexte ?
  • Answer Relevancy : la réponse répond-elle vraiment à la question posée ?
  • Context Precision : les chunks récupérés sont-ils pertinents (pas de bruit) ?
  • Context Recall : les chunks couvrent-ils toute l'information attendue ?
  • Answer Correctness : score global de justesse vs ground truth

Évaluation par composant

  • Router : accuracy binaire (source correcte ? difficulté correcte ?)
  • Retrieval : context precision + recall après pipeline complet
  • Re-ranking : amélioration de precision/recall AVANT vs APRÈS re-ranking
  • Grading : matrice de confusion (TP/TN/FP/FN) vs juge externe
  • Rewriting : gain de precision/recall après reformulation + taux de flip OUI/NON
  • Generation : faithfulness (réponse ancrée dans le contexte)

    Note over AG: Node 1 : identify_sources
    AG->>LLM: Analyse question (source + difficulté)
    LLM-->>AG: sources=ENS.pdf, difficulté=1

    Note over AG: Node 2 : retrieve (difficulté=1 → pas de HyDE)
    AG->>RET: retrieve(question, sources=["ENS.pdf"], difficulty=1)

    Note over RET: Recherche sémantique
    RET->>VDB: MMR search (k=25, fetch_k=100, filter=ENS.pdf)
    VDB-->>RET: 25 chunks sémantiques

    Note over RET: Recherche lexicale
    RET->>RET: BM25 search → 25 chunks lexicaux

    Note over RET: Fusion RRF
    RET->>RET: score = 1/(60+rang_sem) + 1/(60+rang_bm25) → 15 chunks

    Note over RET: Dédoublonnage (Jaccard > 0.8)

    Note over RET: Re-ranking
    RET->>CE: Score (question, chunk) × 15 paires
    CE-->>RET: Scores triés → top 5 (seuil > 0.5)

    RET-->>AG: 5 chunks finaux (score max: 0.9924)

    Note over AG: Route : difficulté=1 → generate direct

    Note over AG: Node 6 : generate
    AG->>LLM: Prompt + contexte (5 chunks) + question
